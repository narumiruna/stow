# Stow v0.1 Implementation Plan

## Goal

Ship a local-first universal content inbox for iOS, iPadOS, and macOS that captures links, text, code, images, and supported files; synchronizes them through the user's private iCloud database; and makes them searchable and reusable through the app, share extensions, and macOS quick panels.

## Context

- The repository currently contains only `README.md`, `.gitignore`, and `LICENSE`; there is no Xcode project or application code.
- The supplied v0.1 product specification is the behavioral source of truth.
- The development machine currently has Swift 6.3.3 command-line tools, but `xcodebuild` cannot run because a full Xcode developer directory is not selected.
- SwiftData sets a practical minimum of iOS/iPadOS 17 and macOS 14 unless the persistence approach changes.

## Architecture

- **Targets:** one shared SwiftUI application codebase with iOS/iPadOS and macOS app targets, plus separate iOS and macOS share-extension targets. Target-specific adapters own `NSItemProvider`, AppKit/UIKit, global-hotkey, drag/drop, Quick Look, and open/copy behavior.
- **Core boundary:** `StowCore` owns versioned SwiftData models, repository operations, capture normalization, lifecycle transitions, retrieval accounting, attachment coordination, search contracts, and metrics contracts. UI targets consume these APIs rather than writing models directly.
- **Persistence and sync:** the host app owns CloudKit synchronization with the private database. App and extensions exchange local captures through an App Group. An early spike must validate whether an extension can safely write the shared SwiftData store while only the host enables CloudKit; if not, extensions will atomically spool `CaptureDraft` manifests and attachments for host ingestion.
- **Data model:** `StowItem` stores searchable metadata and lifecycle state; `StowAttachment` stores binary payloads with external storage plus MIME/UTType, filename, dimensions, and byte count. Stable UUIDs provide identity. CloudKit-compatible defaults and optional relationships are required from schema v1.
- **State:** `status` is exactly `inbox`, `archived`, or `trashed`; pinning and retrieval history remain orthogonal. Trashed items retain `trashedAt` and are purged after 30 days.
- **Search:** search is a device-local derived index rebuilt from synchronized source records. An early benchmark will select Core Spotlight or SQLite FTS5 against one contract: all specified fields, tokenized search, source/date/type filters, deterministic ranking, and acceptable latency. The derived index is never synchronization authority.
- **Attachments:** imported binary data is copied into app-owned storage before the source security scope expires. Reads are coordinated and materialized to temporary files where Quick Look or external apps require URLs. Orphan cleanup is transactional with item deletion.
- **UI:** shared SwiftUI feature views cover Inbox, Recent, Pinned, Archive, Trash, search/filtering, capture preview, and type-specific detail. Platform shells own navigation and presentation conventions.
- **macOS utilities:** a hotkey service presents a quick-capture window for `⌥⇧S` and a non-activating floating retrieval panel for `⌘⇧V`. An optional on-device pasteboard poller saves supported clipboard changes while Stow is running and reports macOS pasteboard access state in Settings.

## Tech Stack

- Swift 6 and SwiftUI
- SwiftData with schema versioning
- CloudKit private database and App Groups
- XCTest and XCUITest
- Uniform Type Identifiers, LinkPresentation, Quick Look, CoreTransferable, and platform pasteboards/workspaces
- OSLog and MetricKit/signposts for diagnostics; no third-party SDK by default

## Non-Goals

- AI features, automatic code classification, recommendations, OCR, code execution, or syntax analysis
- Full webpage snapshots, collaboration, complex folders, browser extensions, or non-Apple clients
- Guaranteed inline preview for unsupported file types
- A full-screen card-only triage workflow

## Assumptions

- v0.1 may require iOS/iPadOS 17+ and macOS 14+.
- The user has iCloud Drive/CloudKit available; the app remains usable locally when iCloud is disabled or offline.
- Code language is optional user-entered metadata; syntax highlighting uses a bundled, non-executing renderer or a small audited dependency selected before implementation.
- Share-extension saves default to Inbox and require one explicit Save tap; Pin, Save as Code, and Directly Archive are progressive options.
- The default conflict policy is field-level last-writer-wins as provided by SwiftData/CloudKit, while immutable attachment identity prevents silent binary replacement.

## Unknowns

- Apple developer team, bundle IDs, App Group ID, CloudKit container ID, and final signing/provisioning ownership.
- Whether shared-store extension writes are reliable with the chosen SwiftData/CloudKit configuration; the capture spike is a blocking architecture gate.
- Whether Core Spotlight or SQLite FTS5 best satisfies in-app result consistency and filtering; the search spike is a blocking implementation gate.
- Whether product metrics remain on-device/exportable or use an approved first-party endpoint. A third-party analytics destination would conflict with the stated privacy promise and requires explicit product approval.
- Final limits for attachment size, import duration, and total local storage.

## Risks

- **Data loss at extension termination:** make capture persistence atomic, retain staged files until commit, and test forced cancellation and low-memory paths.
- **CloudKit schema incompatibility:** use versioned schemas, CloudKit-safe model definitions, development-container tests, and a production schema deployment checklist.
- **Large attachment pressure:** stream copies, enforce documented limits, generate thumbnails off the main actor, and expose actionable failures without creating partial records.
- **Sync conflicts or duplicates:** use stable IDs, idempotent ingestion, explicit timestamps, and two-device conflict/offline test matrices.
- **Global shortcut conflicts:** detect registration failure, explain it in Settings, and let users assign alternatives while preserving the specified defaults.
- **Search drift:** treat the index as disposable, update it after repository commits, and provide startup/manual repair with consistency tests.
- **Scope expansion:** gate release against the v0.1 acceptance checklist and defer non-goals rather than adding adjacent workflows.

## Rollback / Recovery

- Keep schema v1 additive and migration-tested; do not deploy a production CloudKit schema until local migration, clean-install, and two-device sync checks pass.
- Preserve the previous TestFlight/App Store build for rollback. Because CloudKit production schemas cannot be removed, roll back application behavior rather than destructive schema changes.
- Make the local search index and thumbnail cache rebuildable from SwiftData records.
- Keep extension capture staging files until repository commit succeeds; retry idempotently on next host launch and quarantine malformed manifests for diagnostics.
- Before release, verify that deleting/reinstalling one client can restore synchronized records and attachments from another device without duplicating items.
